# MIDox implementation of the ALMaSS *Osmia bicornis* model

**Christopher J. Topping, Ewa Ziółkowska and Xiaodong Duan**

This site documents the C++ implementation of the agent-based *Osmia bicornis* population model
within ALMaSS (Animal, Landscape and Man Simulation System). It combines an implementation-level
narrative with searchable class, method, configuration and source-code documentation generated by
Doxygen.

The source code is the authority for implemented behaviour. The published
[Formal Model](https://doi.org/10.3897/fmj.4.102102) is used as a conceptual comparator. Calibration
and model evaluation are treated as separate work: calibration information is used here only where
it explains the provenance of the post-calibration implementation.

@anchor midox_abstract
## Abstract

Formal model descriptions do not by themselves establish that executable code implements the stated
biological processes. This documentation describes the post-calibration implementation of an
agent-based population model of the red mason bee, *Osmia bicornis*, within ALMaSS. The model
represents development from egg to adult, temperature-dependent phenology, nest-site availability,
resource-limited cell provisioning, maternal sex allocation, dispersal, mortality, parasitism and
optional pesticide exposure. The implementation uses a hierarchy of life-stage classes coordinated
by a population manager and linked to persistent nest objects embedded in a dynamic agricultural
landscape. Individual behaviour operates on a daily time step, while hourly weather observations
determine the time available for flight and foraging. Comparison with the Formal Model identifies
changes in developmental parameterisation, foraging search, nest-density scaling and the treatment
of optional processes. The documentation distinguishes operational behaviour from inactive code and
retained limitations. Its purpose is to make the implemented model inspectable and reproducible; it
does not replace the separate account of calibration and evaluation.

@anchor midox_introduction
## 1. Introduction

The red mason bee is a univoltine solitary bee whose reproduction depends on the coincidence of
suitable nesting cavities, adequate floral resources and weather that permits flight. These processes
operate at different spatial and temporal scales and are affected by agricultural management. The
*O. bicornis* model was developed within ALMaSS so that individual development and behaviour could
respond to daily weather, spatially explicit resources, land use, farm operations and pesticide
exposure.

MIDox documents the executable implementation that lies between a Formal Model and subsequent model
testing. The [Formal Model](https://doi.org/10.3897/fmj.4.102102) defines the conceptual entities,
processes and equations. This site records how those elements are represented in C++, including where
the implementation has subsequently changed. Calibration and testing address a different question:
whether a particular parameterisation produces the required empirical patterns. Their methods and
results are therefore outside the scope of this implementation reference.

The implementation is a component of ALMaSS rather than a stand-alone program. The files documented
here depend on the complete framework for landscape data, weather, farm events, object management,
pesticide fate and the main scheduling loop. The present repository can be used to inspect the
*Osmia* component and generate its documentation. Simulation runs require the corresponding complete
ALMaSS source and input data.

@anchor midox_scope
### 1.1 Scope

The implemented life cycle comprises egg, larva, prepupa, pupa, adult in cocoon and free-living adult
female. Males are represented as brood but do not become free-living agents because females alone
perform nesting and provisioning. Population dynamics arise from stage development and mortality,
female lifespan and fecundity, cell provisioning, offspring sex and mass, nest-site availability,
parasitism and optional pesticide effects.

The model does not resolve flower species preference, mating behaviour or a free-living male
population. The current foraging path reads pollen availability from the landscape but does not
remove the collected quantity from that resource. The optional mechanistic parasitoid subsystem is
present in the source but is disabled by default and is not safe to enable in its current form.

@anchor midox_architecture
## 2. Architecture

@anchor midox_entities
### 2.1 Individual agents and stage transitions

@ref Osmia_Base "Osmia_Base" stores attributes shared by all bee stages, including spatial position,
age, mass, parasitism state, the current state-machine value and links to the population manager and
nest. The developmental classes form an inheritance chain:

@ref Osmia_Egg "Osmia_Egg" &rarr; @ref Osmia_Larva "Osmia_Larva" &rarr;
@ref Osmia_Prepupa "Osmia_Prepupa" &rarr; @ref Osmia_Pupa "Osmia_Pupa" &rarr;
@ref Osmia_InCocoon "Osmia_InCocoon" &rarr; @ref Osmia_Female "Osmia_Female".

The hierarchy follows ontogeny rather than placing the life stages as siblings beneath a common
stage class. Later stages consequently inherit members introduced for earlier stages. The advantage
is that a stage needs to override only the behaviour that changes. The disadvantage is that the
meaning of an inherited accumulator can change between stages and later classes retain data that
they no longer use.

A transition between life stages constructs a new object rather than changing the C++ type of an
existing object. The current stage copies the transferable attributes into @ref struct_Osmia
"struct_Osmia". @ref Osmia_Population_Manager::CreateObjects(TTypeOfOsmiaLifeStages,TAnimal*,struct_Osmia*,int)
"Osmia_Population_Manager::CreateObjects()" constructs the successor, the nest cell is redirected to
the new object where applicable, and the predecessor is removed. The transfer record therefore
defines which attributes persist across stage boundaries.

@anchor midox_population_manager
### 2.2 Population-level control

@ref Osmia_Population_Manager "Osmia_Population_Manager" connects the species implementation to the
ALMaSS daily scheduling contract. It reads and caches configuration values, initialises nests and the
starting population, calculates daily environmental quantities, constructs age- and mass-dependent
lookup tables, creates new stage objects and records optional outputs. Species parameters are stored
largely as static class members, so all individuals in a run share one parameterisation.

The manager also holds the daily mean temperature, available foraging hours and seasonal flags used
by the life-stage classes. Thread-specific counters are used for recruitment and mortality outputs.
Nest allocation is protected separately because several females may search the same landscape
polygon during a parallel population step.

@anchor midox_nests
### 2.3 Nests and spatial organisation

@ref Osmia_Nest_Manager "Osmia_Nest_Manager" maintains potential nesting capacity by landscape
polygon. Habitat-specific input densities are multiplied by an intentional operational factor of
0.001 before they become model capacity. @ref OsmiaPolygonEntry "OsmiaPolygonEntry" stores the
capacity and occupancy associated with a polygon, while @ref Osmia_Nest "Osmia_Nest" stores the
brood cells and provisioning records for an individual nest.

Females occupy one nest at a time. A brood cell retains a pointer to the developing individual, and
this pointer is updated at each life-stage transition. A nest can therefore persist after the mother
has died and release its nesting capacity when its brood cells have been resolved. The diagnostic
method `ZeroCells()` has an inverted return polarity; its result is currently ignored and the
limitation is documented in the class reference.

The landscape is polygon based, while individual positions use ALMaSS coordinates in metres.
Foraging queries operate on landscape resource information within square search windows. A 1 km
female-density grid is allocated and cleared daily but is not populated by the current implementation.

@anchor midox_scheduling
## 3. Scheduling and control flow

The ALMaSS framework advances the model in daily steps. Within each day, the population manager runs
its scheduling hooks and the framework advances every live individual until that individual reports
that its daily step is complete.

@anchor midox_daily_schedule
### 3.1 Daily sequence

1. @ref Osmia_Population_Manager::DoFirst() "Osmia_Population_Manager::DoFirst()" reads current
   environmental conditions, calculates flyable hours, refreshes nest availability, clears the
   female-density grid and calculates the temperature-dependent prepupal development rate.
2. @ref Osmia_Population_Manager::DoBefore() "Osmia_Population_Manager::DoBefore()" performs
   pre-step housekeeping and any enabled testing output.
3. The ALMaSS population framework calls each individual's `BeginStep()` and repeatedly calls its
   `Step()` state machine until the individual has completed the day.
4. @ref Osmia_Population_Manager::DoAfter() "Osmia_Population_Manager::DoAfter()" has no
   *Osmia*-specific behaviour in the current implementation.
5. @ref Osmia_Population_Manager::DoLast() "Osmia_Population_Manager::DoLast()" updates the shared
   pre-wintering and overwintering flags and writes optional population-dynamics output.

The ordering is important. Daily weather and nest availability are established before individuals
act, whereas seasonal state changes made in `DoLast()` become available to individuals on the next
daily step. The population may be processed in parallel. Random draws therefore occur within the
order established by the ALMaSS framework and its thread-local random-number services.

@anchor midox_state_machines
### 3.2 Within-stage state machines

The immature stages and the adult in cocoon use a common pattern: initial state, development, stage
transition or death. Each `Step()` method can execute more than one internal state during a day, but
terminates when the class sets its step-completion flag. The adult female adds reproductive
behaviour and dispersal. After pre-nesting, a female searches for a nest; failure sets a dispersal
state, after which one movement is made in a random direction represented by an integer from 0 to 7.

The principal life-stage sequence is:

`Egg -> Larva -> Prepupa -> Pupa -> Adult in cocoon -> Adult female`

A male reaches the adult-in-cocoon stage but is removed at emergence rather than becoming a
free-living agent.

@anchor midox_implementation
## 4. Implementation details

@anchor midox_development
### 4.1 Development and emergence

Egg, larval and pupal development use accumulated thermal units above stage-specific thresholds.
Each stage tests mortality and then adds the current day's contribution to its development
accumulator. When the configured total is exceeded, the stage creates its successor.

Prepupal development is represented differently. @ref Osmia_Prepupa "Osmia_Prepupa" obtains a
daily development increment from a quadratic temperature-response function calculated by the
population manager and normalised at the configured optimum. This increment is divided by the
configured prepupal duration before being added to the stage accumulator. The coefficients are
validated at initialisation because unsuitable overrides could make the rate invalid.

@ref Osmia_InCocoon "Osmia_InCocoon" represents the adult before spring emergence. It separates
pre-wintering, overwintering and spring pre-emergence. The model accumulates degree-days above the
configured thresholds. Accumulated overwintering warmth enters a linear emergence-counter equation,
to which individual variation and a random nest-aspect delay of 0--35 days are added. Males are then
removed; females enter the free-living adult stage.

@anchor midox_reproduction
### 4.2 Adult reproduction and provisioning

@ref Osmia_Female "Osmia_Female" represents the free-living reproductive agent. Adult age is
limited by the configured lifespan. The age-dependent foraging-efficiency, sex-allocation and
first-cocoon-provision tables are created through that configured lifespan, with a minimum extent of
60 days.

@ref Osmia_Female::st_ReproductiveBehaviour() "Osmia_Female::st_ReproductiveBehaviour()" first
obtains or creates a nest and then constructs a plan for the brood cells. A new calibrated egg-number
draw is made for every nest, including the two-egg shift with probability 0.45, and is reduced by two
eggs for every preceding nest. Maternal mass and age determine the planned female proportion and
the initial female provisioning target. Female targets decline through the nest; male targets begin
at the configured male minimum. If no female eggs are planned, every male target remains at that
minimum and no female provision decline is calculated.

Foraging occurs only when the daily weather calculation provides flying time. The current
@ref Osmia_Female::Forage() "Osmia_Female::Forage()" implementation queries square landscape
windows for the most favourable pollen location. The unused legacy radial forage-mask classes and
their three configuration declarations have been removed. Monthly pollen and nectar threshold arrays are loaded but not consulted by the active
search. Travel cost is not included in patch ranking, and pollen collected by *Osmia* is not removed
from the landscape resource in this code path.

Provisioning accumulates until a target and a minimum construction-time condition are satisfied. The
implementation tests that the plan is non-empty before reading its first element. When the maximum
cell-construction time is reached, a cell can still be completed if the male minimum has been
collected. A planned female cell is converted to male if its final provision is below the female
threshold. Provision mass is then mapped to offspring mass.

@anchor midox_movement
### 4.3 Nest search, foraging and dispersal

Nest search operates at polygon level through @ref Osmia_Nest_Manager "Osmia_Nest_Manager". A
female makes a configured number of local attempts. If no capacity is obtained, she enters
@ref Osmia_Female::st_Dispersal() "Osmia_Female::st_Dispersal()". Dispersal distance is drawn from
the configured distribution and scaled by the upper homing-distance value; direction is drawn
uniformly from the eight movement directions. ALMaSS corrects coordinates at the landscape boundary.
Dispersal increments adult age, so it has a direct lifespan cost.

Foraging is centred on the current nest, not the female's transient location. The search retains a
usable location and applies configured give-up rules when local resource levels fall. The detailed
sequence is documented with @ref Osmia_Female::Forage() "Osmia_Female::Forage()" and the associated
reproductive state method.

@anchor midox_mortality
### 4.4 Mortality, parasitism and pesticides

Egg, larval, prepupal and pupal stages apply stage-specific background mortality. The adult in cocoon
applies overwinter mortality, while the free-living female is limited by adult lifespan and can also
be affected by farm-management events and the optional pesticide engine.

The default parasitism calculation is exposure based. When a cell is closed,
@ref Osmia_Female::CalcParaistised(double) "Osmia_Female::CalcParaistised()" scales the probability
of parasitism with the time that the cell remained open and assigns one of two parasitoid outcomes.
The alternative mechanistic path uses a coarse parasitoid-density grid and is selected by a
configuration flag. It is disabled by default and remains internally inconsistent in its monthly
indexing and parasitoid-type mapping; it must not be enabled without correction and testing.

@ref Osmia_Female::OnFarmEvent(FarmToDo) "Osmia_Female::OnFarmEvent()" separates the generic
background response to insecticide or biocide events from the detailed pesticide engine. A
`product_treat` event invokes overspray only when the pesticide engine is enabled; otherwise it has
no biological effect. Detailed pesticide uptake can be recorded when the corresponding compile-time
output option is enabled.

@anchor midox_parameters
## 5. Configuration, inputs and outputs

@anchor midox_configuration
### 5.1 Configuration

The documented source declares 100 unique configuration keys. Their declaration defaults define the
implementation described here; no separate calibrated configuration file is required for this
baseline. The configuration declarations cover development, mortality, emergence, maternal
allocation, nesting, movement, foraging, parasitism, pesticide response, output and technical
control.

The source-verified parameter appendix classifies 72 settings as active, 20 as conditional and eight as
having no effect on current behaviour. This last category includes declarations that are never read
and retained settings bypassed by the active algorithm; it is therefore broader than a simple search
for unreferenced keys. Fifteen declaration defaults differ from the Formal Model. The appendix records
every key, default, comparator, provenance category and implementation status.

@anchor midox_inputs
### 5.2 Inputs

The *Osmia* component receives most environmental information through ALMaSS rather than reading it
directly. Required information includes the spatial landscape, habitat classification, hourly and
daily weather, flowering-resource information, farm-management events and the initial population.
The nest manager additionally reads the habitat-specific nest-density file selected by
`OSMIA_NESTBYLEDATAFILE` (declaration default `OsmiaNestsByHabitat.txt`). Input preparation and the
complete ALMaSS file specifications belong to the framework documentation; this component documents
only the values it requests and how they affect *Osmia* behaviour.

@anchor midox_outputs
### 5.3 Outputs

Standard population output is provided by the ALMaSS population framework. The component can also
write a configured population-dynamics file containing daily recruitment and mortality counts by
life stage. Additional files are compiled or enabled for testing, calibration or pesticide tracing,
including stage lengths, female weights, egg distributions, overspray, contact and pesticide intake.
These diagnostic files are not all produced in a default build and should not be treated as a stable
public output interface without checking the compile-time options.

@anchor midox_differences
## 6. Implementation differences and retained limitations

The post-calibration implementation is not identical to the Formal Model. The principal differences
relevant to interpretation are:

- developmental thresholds and totals use the declaration defaults in the current source;
- prepupal development uses a normalised non-linear temperature-rate function;
- adult foraging uses square-window resource searches; the unused radial masks have been removed;
- monthly pollen and nectar thresholds are stored but do not affect patch choice;
- habitat nest densities are multiplied by the intentional 0.001 operational scale;
- dispersal uses a random direction from the eight available movement directions;
- the age- and mass-dependent maternal allocation tables include defensive bounds for the permitted
  body-mass range and configured lifespan;
- the optional mechanistic parasitoid subsystem extends beyond the Formal Model but is not currently
  operational.

Other limitations should be considered when using the model. Pollen is not depleted by the active
foraging path, the female-density grid is inactive, males are not free-living agents, and the current
source contains optional testing and pesticide paths controlled at compile time. Full population
testing, sensitivity analysis and empirical evaluation are reported separately from this
implementation documentation.
